# anygrep 設計メモ（v0.1）

English: [how-it-works.md](how-it-works.md), [usage.md](usage.md), [relevance.md](relevance.md), [benchmarks.md](benchmarks.md).

## 目的と位置づけ

- 対象は「ノート・PDF・スクリーンショットを、ひとつのローカル索引とひとつのモデルで意味検索する」こと。API キーも GPU も使わない。
- 写真ライブラリの代替は狙わない。CPU では画像 1 枚の埋め込みに 1〜2 秒かかるため、数万枚の写真を扱うには遅い。
- 配布は `pipx install anygrep` / `uv tool install anygrep` の 1 コマンドで完結させる。対象は Linux / macOS / Windows。

## 名前

- `anygrep` を選んだ。「何でも（テキスト、PDF、画像）を grep する」という意味で、短く、機能が伝わる。
- 確認日 2026-10-09 の時点で、PyPI・npm・crates.io・Homebrew のいずれにも同名パッケージはなかった。
  - GitHub には `puruneko/anyGrep` がある（0★、Nim、Office ファイル向けの grep）。
  - 古いユーザー名 `anygrep` も存在する。
  - どちらも衝突するほどではないと判断した。
- 「Gemma」「Google」を名前の頭に置くと商標上のリスクがあるため避けた。
- 他の候補（`semdex`、`omnigrep`、`fossik`）は、既存の同名リポジトリがあるか、意味が伝わりにくいので見送った。

## モデルと推論経路

- モデルは EmbeddingGemma 2 で、onnx-community が変換した int8 ONNX（`*_quantized.onnx`）を使う。必要なファイルは次の 2 組だけ。
  - テキストモデル: 346 MB（トークナイザ 32 MB を含む）
  - vision encoder: 195 MB（画像を扱うときだけ読み込む）
  - audio encoder は読み込まない。
- 依存ライブラリは onnxruntime、tokenizers、numpy、Pillow、pypdfium2、pathspec、platformdirs、tqdm。
  - PyTorch と transformers は入れない。pipx で入れた環境の大きさは約 213 MB。
  - 下限は onnxruntime>=1.23、tokenizers>=0.20。固定したリビジョンの int8 グラフ（GatherBlockQuantized の `bits` 属性）と tokenizer.json は、これより古い版では読み込めない。読み込みに失敗したときは、入っている版を示すエラーを出して終了する。
  - certifi も依存に入れる。python.org の macOS 版 Python は CA 証明書を持たないことがあり、システムの CA が見つからないときだけ certifi の証明書を使う。
  - `huggingface_hub` は tokenizers の依存として入るだけで、anygrep 自身は使っていない。
- int8 を選んだ理由（事前ベンチマークより）
  - torch fp32 よりテキストで約 2 倍、画像で約 1.4 倍速い（4 スレッド、アイドル時の推定値）。
  - fp32 とのコサイン類似度は 0.9986 以上。
  - q4 は短いクエリ 1 件では int8 より速い（38 ms と 97 ms）が、文書と画像では遅く、画像の埋め込みは fp32 からのずれが大きい（コサイン 0.988）。モデルを 1 つにするため int8 にした。
- 画像の前処理は、transformers の Gemma4ImageProcessor を numpy で移植した。
  - 縦横比を保ったまま、`budget × 9` パッチ以内に収まり、辺が 48px の倍数になるサイズへ bicubic でリサイズする。
  - 画素は [0,1] に正規化して 16×16 のパッチに切り、各パッチに (x, y) の位置 ID を付ける。
  - パディングはしない。1 枚ずつ処理するので不要で、処理量も減る。
  - 検証結果: transformers 経由の参照埋め込みと比べて、コサイン類似度は 3 枚 × 予算 2 種類（140・280）で 0.99995 以上、テキストのクエリ・文書では 1.0000 だった。
- 入力系列の組み立て
  - トークナイザは `encode_special_tokens = True` で使う。本文に `<|image|>` や `<eos>` という文字列があっても制御トークンにせず、ただの文字として扱う（画像特徴なしの `<|image|>` は ORT のエラーになり、`<eos>` は埋め込みを壊すため）。
  - テキスト: `[BOS] 接頭辞 + 本文 [EOS]`
  - 画像: `[BOS][BOI] <|image|>×n [EOI][EOS]`
  - どちらも同じ言語モデルのグラフに通すので、テキストと画像は同じ 768 次元空間に入る。
- 接頭辞
  - 検索クエリ: `task: search result | query: `
  - 文書: `title: <拡張子なしのファイル名> | text: `
    - モデルカードの既定は `title: none` だが、ファイル名は手がかりとして有効なことが多いので使った。
- ORT の設定
  - intra-op スレッドは `--threads`、inter-op は 1、逐次実行。
  - メモリアリーナは無効にした。vision の attention バッファが大きく、アリーナを使うと RSS が膨らむため。
  - 既定のスレッド数は「論理 CPU 数の半分、最大 8」。

## 画像のトークン予算

- 既定は 140。オプションで 70（速さ優先）と 280（文字の多い画像向け）を選べる。
  - 事前ベンチマーク（小物体・小文字の 50 枚）の top1 は、280 で 0.88、140 で 0.90、70 で 0.78。
  - 速度は、140 が 280 の約 2.5 倍、70 が 280 の約 4〜5 倍。
- 予算が変わると埋め込みも変わる（予算どうしのコサイン類似度は 0.85〜0.96）。そこで次のように扱う。
  - 予算は索引のメタ情報に保存する。
  - 画像ごとにも、どの予算で埋め込んだかを記録する。
  - 予算を変えて `index` を実行すると、記録と異なる予算の画像だけを埋め込み直す。
  - 索引のメタ情報の予算は、画像を処理した実行が中断されずに終わったときだけ更新する（`--no-images` の実行や Ctrl-C で中断した実行では変えない）。
  - 変更中の予算は `image_budget_pending` として先に保存する。中断したあと引数なしの `index` を実行すると、元の予算に戻さずに変更を最後まで続ける。
  - 画像クエリは、索引にある画像で最も多い予算で埋め込む（途中で中断して予算が混在している場合に備える）。`status` は混在していればそれを示す。

## 保存形式と検索

- SQLite のファイル 1 つに、WAL モードで保存する。テーブル構成は次のとおり。
  - `meta`
  - `roots`
  - `files`: パス、種類、サイズ、mtime_ns、sha256、予算、状態、メモ
  - `chunks`: ページ、行範囲、本文、ベクトル
  - `chunks_fts`: 本文の文字一致用の FTS5 索引（次の「文字一致」を参照）
- ベクトルは 768 次元のまま、正規化して float16 で保存する（1 チャンクあたり 1.5 KB）。
  - MRL で次元を縮めた場合を、デモコーパスの 12 クエリで比べた。

    | 次元 | top1 正解 | 768 次元との top5 一致率 |
    |---|---|---|
    | 768 | 12/12 | — |
    | 512 | 11/12 | 0.85 |
    | 256 | 11/12 | 0.88 |
    | 128 | 12/12 | 0.67 |

  - 容量の差は小さい（10 万チャンクで 150 MB と 50 MB）。品質を優先して 768 次元にした。
  - 次元を縮める実装は、必要になってからでも後付けできる。
- 検索は numpy による総当たりのコサイン類似度。
  - 10 万 × 768 の行列積でも数十 ms で済む。
  - SQLite からの読み込みのほうが支配的になる。
- 種類の絞り込みは SQL で行う。パスの絞り込み（前方一致または glob）とクエリ画像自身の除外は numpy 側で行う。
- 既定では 1 ファイルにつき最良のチャンク 1 件を表示する。すべて見たいときは `--chunks`。
- 順位は種類をまたいだコサイン類似度のまま付ける。デモでは 12/12 で正解が 1 位だった。
- 弱い一致は既定で隠す（次節）。

### 文字一致（exact）

- 意味の近さでは探せない手がかり（請求書番号、エラーコード、型番、ファイル名）のために、3 文字以上のテキストクエリは、そのままの文字列としても探す。大文字と小文字は区別しない。
  - 本文: SQLite FTS5 の trigram トークナイザの索引 `chunks_fts` で候補を引き、チャンクの本文に文字列が含まれるかを Python で確かめる。trigram は日本語でも空白で区切らずに使える。2 文字以下は候補が多すぎ、trigram でも引けないので、意味検索だけにする。
  - ファイル名: 検索したフォルダ（`--everywhere` では索引したフォルダ）からの相対パスに含まれるか。対象のファイル数だけの文字列比較なので、索引は使わない。
- 一致したファイルは、スコアが弱判定でも必ず含め、それ以外の結果より上に、意味のスコア順で並べる。スコアに一致の点数を足して混ぜることはしない。根拠のある重みを決められないため。上位に置くだけなので、意味の順位はそのまま残る。
  - 表示は 1 ファイル 1 件のまま。代表のチャンクは、文字列を含むチャンクのうち最もスコアが高いもの（スニペットに文字列が出る）。名前だけが一致したときは、そのファイルの最良のチャンク。
  - パス・glob・種類の絞り込みと `-m` は通常の結果と同じに効く。画像クエリでは文字一致を行わない。正規表現や grep のオプションは実装しない。
- `chunks_fts` は `content='chunks'` の外部コンテンツ表で本文を二重に持たず、`detail='none'` で位置情報も持たない。候補は LIKE で引く（trigram 表の LIKE は索引を使う）。`detail='full'` にすると引用符付きのフレーズで MATCH できるが、合成コーパスで索引が本文の約 3.6 倍になった。`none` では約 0.9〜1 倍。どちらでも候補は本文で確かめるので結果は変わらない。
  - SQLite の LIKE は ASCII 以外の大文字小文字を同一視しないので、クエリの小文字・大文字・先頭大文字の形でも引く。
  - チャンクの追加・削除と同じトランザクションで更新する。画像のチャンク（本文なし）も行を持つ。FTS5 の整合性検査が外部コンテンツの全行を求めるため。
- 互換性
  - FTS5 の trigram（SQLite 3.34 以降）が使えない環境では、意味検索だけで動き、`anygrep status` に 1 行出す。
  - この表ができる前の索引は、writer（`index`、検索前の索引、API の `update()`）が開いたときに表を作り、既存のチャンクを数千件ずつのトランザクションで追加する。中断しても残りから続く。終わるまでの検索は、表にまだないチャンクの本文を直接読んで探す。処理世代は上げない。保存済みの本文から作れ、ベクトルを作り直す必要がないため。
  - FTS5 のない SQLite の writer が書き込んだ索引は、表が古くなるので印を残し、次に FTS5 のある writer が表を空にして作り直す。
- 実測（Ryzen 7 7700、nice 19）
  - 合成テキスト 2,000 ファイル（本文約 20 MB）: 索引ファイルは 47.7 MB から 70.2 MB（+47%）。保存側の時間は、埋め込みを省いた計測で 6.5 秒から 14.3 秒（+7.9 秒、1 ファイル約 4 ms）。実際の埋め込みはこのコーパスで 1 時間以上かかるので、全体の 0.2% 未満。既存の索引への後からの追加は 5.4 秒。
  - デモコーパス（23 ファイル、実モデル、8 スレッド）: 索引ファイルは 0.12 MB から 0.18 MB。索引の時間は 14.5 秒と 14.1 秒で、差は測定の揺れより小さい。
  - 一致の検索は 1〜36 ms（候補が 1,500 チャンクでも）。表がない索引で本文を直接読むと約 90 ms。

## 関連度のしきい値

- 問題: 関連の薄いクエリでも、無関係な画像が 0.6 前後で上位に混ざる（hubness）。また、コサインの値域はクエリと結果の種類の組で違う（テキスト→画像は低め、画像→画像は高め）。単一のしきい値では、画像の雑音を落とそうとするとテキストの正解まで消える。
- 判定（`src/anygrep/thresholds.py`）: 次の両方を満たす結果だけを表示し、それ以外を「弱い一致」とする。
  1. 種類の組ごとの最低スコア以上。画像が関わる組は画像のトークン予算ごとに値を持つ。
  2. クエリの「基準値」より、組ごとのマージン以上高い。基準値は、同梱の参照集合（`src/anygrep/reference.npz`）に対するそのクエリのスコアの中央値。参照集合は `scripts/build_reference_set.py` で作る、話題も書式もばらばらな文章 64 件（英語、日本語、コード、ログ、表、メールなど）と合成画像 12 枚（予算 70・140・280 ごと）。結果がテキストか PDF なら文章の、画像なら画像の基準値を使う。
- 基準値を使う理由
  - 「asdf」「hello」「...」のような意味のないクエリや短いクエリは、何に対してもスコアが少し高くなる。最低スコアだけでは、その上位が通ってしまう。
  - 以前は「索引にある同じ種類のチャンクの中央値 + 0.04」を使っていたが、2 つの問題が見つかった。
    - 1 つの話題に偏ったフォルダ（同じ話題のノートが大半）では、中央値そのものが正解のスコアになり、正解まで弱い一致になった。サワードウのノート 8 件と無関係なノート 2 件のフォルダで「sourdough bread」で表示されたのは 8 件中 2 件だけだった（行が 8 件以上になると条件が効くので、無関係なファイルを 1 件足しただけで結果が消えることもあった）。
    - 実際のコーパス（コードや日本語を含む 253 ファイル）では、中央値が高めなのに差が 0.04 しかなく、「asdf」「???」で 10 件ずつ表示された。
  - 参照集合は索引の中身に依存しないので、1 つめの問題は起きない。マージンを組ごとに較正したことで、2 つめも大きく減った（下記）。
  - 参照集合はモデルのリビジョンと一緒に保存し、リビジョンが一致しないときは基準値を使わない（最低スコアだけになる）。テストで一致を確認している。
- 表示: 弱い一致は既定で隠す。`--weak` で表示し `(weak)` と印を付ける（このときは一致として数え、終了コードは 0）。端末への出力で 1 件も残らないときは空にせず「No strong matches; showing the closest results.」と出し、上位 3 件（`-m` を明示したときは `-m` 件、最大 10 件）を弱い一致として示す。終了コードは 1 のまま。パイプ出力、`-l`、`--json` には `--weak` なしで弱い一致を出さない（スクリプトが弱い結果を一致と誤解しないため）。`--json` は `score` と `weak` を必ず含む。
- 較正（`scripts/calibrate_thresholds.py`、結果は `docs/calibration-results.json`）
  - コーパス: デモコーパスに、合成のノート 4 件、PDF 1 件、画像 8 枚を足したもの（すべてスクリプト内で生成）。
  - クエリ: 正解ファイルを付けたテキスト 47 件と画像 9 件。無関係なクエリとして、話題外のテキスト 15 件、無意味な文字列や短いクエリ 21 件（「asdf qwer zxcv」「???」「the」「hi」「1234」「あ」「えーと」など）、画像 4 件（ノイズ、灰色一色、縞、市松）。
  - 各ファイルのスコアは最良チャンクのもの（既定の検索表示と同じ）。
  - 最低スコアの選び方: 正解の再現率 0.95 以上を保つ最大値（0.01 刻み）。ただし無関係クエリの最高スコアを 0.01 単位で切り上げた値は超えない。
  - マージンの選び方: 最低スコアを通る正解について、再現率 0.95 以上を保つ最大値（0.01 刻み）。無関係クエリによる上限は付けない。上限を付けると、このコーパスの無関係クエリをぎりぎり落とすだけの小さな値（text→pdf で 0.01 など）になり、ホールドアウトで無意味なクエリが通ったため。
  - 同じ規則を、値を選ぶのに使っていないホールドアウトのコーパス（`scripts/heldout_corpus.py`、すべて合成）でも評価する。混在フォルダ（ノート、コード入りの README 風ノート、日本語のノート、PDF、画像 14 枚）、レシピ 10 件、サワードウ 8 件 + 無関係 2 件、空き家政策の日本語ノート 6 件の 4 つ。
- 結果（較正コーパス、予算 140。R = 再現率、P = 適合率。P は正解以外をすべて誤りとして数えるので、関連はあるが正解ラベルのないファイルも誤りに入る）

  | 組 | 最低スコア 70 / 140 / 280 | マージン | 正解の最小 / 中央値 | 正解の基準値との差の最小 | R | P（しきい値なし → 最低スコアのみ → 両方） |
  |---|---|---|---|---|---|---|
  | text→text | 0.62 | 0.10 | 0.626 / 0.724 | 0.075 | 0.96 (27/28) | 0.02 → 0.46 → 0.87 |
  | text→pdf | 0.64 | 0.11 | 0.648 / 0.742 | 0.118 | 1.00 (10/10) | 0.03 → 0.91 → 0.91 |
  | text→image | 0.63 / 0.62 / 0.62 | 0.06 | 0.607 / 0.741 | 0.065 | 0.96 (22/23) | 0.02 → 0.12 → 0.50 |
  | image→image | 0.76 / 0.75 / 0.70 | 0.09 | 0.760 / 0.886 | 0.099 | 1.00 (9/9) | 0.04 → 0.41 → 1.00 |
  | image→text | 0.62 / 0.62 / 0.55 | 0.04 | 0.622 / 0.651 | 0.048 | 1.00 (2/2) | 0.01 → 0.14 → 0.15 |
  | image→pdf | 0.62 / 0.62 / 0.61 | 0.13 | 0.714 | 0.140 | 1.00 (1/1) | 0.02 → 0.12 → 1.00 |

- 規則ごとの比較（正解の表示数 / 何かが表示される無関係クエリの数）

  | データ | 旧規則（中央値 + 0.04） | 新規則（基準値 + マージン） |
  |---|---|---|
  | 較正コーパス、予算 140（無関係 40 件） | 72/73, 11/40 | 71/73, 0/40 |
  | 較正コーパス、予算 70 | 72/73, 11/40 | 70/73, 0/40 |
  | 較正コーパス、予算 280 | 71/73, 22/40 | 70/73, 2/40 |
  | ホールドアウト 4 コーパス計、予算 140（無関係 34 件） | 64/72, 8/34 | 67/72, 2/34 |
  | うちサワードウ（「sourdough bread」の正解 8 件を含む 12 件） | 5/12 | 9/12 |

  - 較正コーパスで新たに隠れる正解は「running out of disk space」→ docker のチートシート（0.634、基準値との差 0.075）。旧規則でも隠れていたのは「when is the piano lesson」→ カレンダーのスクリーンショット（0.607）。
  - ホールドアウトで通る無関係クエリは「offside rule in ice hockey」と「相撲の番付の決め方」で、どちらもチェス盤の画像（0.648、0.635）。画像はさまざまなクエリの上位に出やすい。
  - ホールドアウトで隠れる正解は 5 件。サワードウの 2 ノート（発酵の話で sourdough という語を含まず、0.616 と 0.605 で最低スコアに届かない）と、そのうち 1 件の別クエリ、言語交換のノート（0.618）、気温の折れ線グラフ → 株価の折れ線グラフ（画像クエリ、境界的な正解）。
  - 参考（リポジトリには入れていないデータ）: 実在の README や PDF を含むホールドアウト（レビューで使用、27 テキスト・6 PDF・14 画像）では、旧規則 61/61・無関係 13/24 → 新規則 60/61・4/24（うち「テスト」は試験の PDF などに実際に一致しており、誤りではない）。手元の実ファイル 253 件の索引では「asdf」の表示が 10 件 → 1 件、「qwzx plorb fnord」が 10 件 → 0 件で、実際の 18 クエリはすべて結果を表示した（平均 9.6 件）。
- 限界: コーパスはどれも小さく合成で、画像クエリの正解は特に少ない（image→text は 2 件、image→pdf は 1 件）。実際のコレクションでは境界付近の正解が隠れることがあるので、`--weak` を案内している。

## ほぼ同じファイルのまとめ表示

- 問題: 同じノートのコピー、書き出した版、少し直した版、縮小したスクリーンショットが、別々に上位を占めて `-m` の枠を使ってしまう。
- 判定（`src/anygrep/search.py` の `is_near_duplicate`）: 種類（text / pdf / image）が同じで、次のどちらかを満たす 2 ファイルを「ほぼ同じ」とする。
  1. SHA-256 が同じ（索引時に保存済み）。
  2. クエリに最も合ったチャンクどうしのコサインと、ファイルごとのチャンクベクトルの平均（正規化）どうしのコサインが、どちらも種類ごとのしきい値以上。text と pdf は 0.95、image は 0.98。
  - 平均ベクトルも見るのは、長いノートで 1 節だけが同じ別のノート（最良チャンクだけが一致する）をまとめないため。
  - text と pdf は、さらに単語の置き換えが少ないことを求める。索引時に、ファイルの本文を単語列（日本語・中国語・韓国語は 1 文字ずつ）にして、隣り合う 2 語の組のハッシュのうち小さい方から 256 個を署名として保存する（`src/anygrep/signature.py`、bottom-k スケッチ、1 ファイル 1 KB）。検索時は 2 つの署名から「含まれる側の単語の組のうち、もう一方にない割合」を推定し、18% 以下（`DUP_MAX_CHANGED`）のときだけまとめる。含まれる側で測るので、行の追加・削除は数えない。単語を 1 つ置き換えると組は 2 つ変わるので、18% は単語の置き換え約 10% に当たる。
    - 理由: 同じ書式の月次の給与明細や銀行明細は、月と金額だけが違うので埋め込みではほぼ同じ（コサイン 0.96〜0.98）になり、12 か月分が 1 件にまとまっていた。単語の置き換えは明細どうしで 14〜36%（組の変化は 28% 以上）、意図したコピーでは最大 5%（分量を変えたレシピ、組の変化 10%）で、ライ麦版のサワードウは単語 9.4%・組 11%。
    - 以前は本文全体を `difflib` で比べていたが、同じ書式の長い文書（8,000 語の報告書 20 件）では検索 1 回に 8〜48 秒かかった。署名の比較は 1 組数マイクロ秒で、本文は読まない。0.1.0 で作った索引のファイルには署名がないので、必要になったときだけ保存済みのチャンク本文から作る。
  - 種類が違えば（同じ文章の .md と PDF など）まとめない。
- 表示: 既定では、グループの中で最上位のファイルを代表として 1 行で示し、その下に `(+2 similar: path, path)` と出す（パスは 3 件まで）。まとめた分は後続の結果で埋め、異なる結果が `-m` 件になるまで探す。`--no-collapse` で無効にする。`--json` は代表の各結果に `similar`（スコア、パス、位置などを持つ配列）を付け、まとめたファイルをすべて残す。`--chunks` ではまとめない。
- 探し方: スコア順に、ファイルごとの最良チャンクを見て、既存のグループの代表と比べる（代表とだけ比べるので、連鎖的には広がらない）。SHA-256 と平均ベクトルは、見たファイルの分だけ SQLite からまとめて読む。`-m` 件そろったあとも 10 ファイル先まで見て、代表のコピーを拾う。異なる結果を探すのは、既存のグループに入らなかったファイルが `n × 20 + 100` 件になるまで。グループに入ったファイル（同じ LICENSE が数百件など）はこれに数えず、別にその 10 倍まで見る。以前はまとめたコピーも数えていたため、同じファイルが 400 件上位にあると `-m 10` で 1 件しか返らなかった。
- 速度: 10 万チャンク（2 万ファイル）の合成索引で、検索 1 回は有無とも約 0.9 秒で差は測れなかった（ベクトルの読み込みが支配的）。下記の 123 ファイルの索引では、まとめなしが 0.7 ms、まとめありが 2.2 ms（署名の比較を含む）。
- 較正（`scripts/measure_duplicates.py`、結果は `docs/duplicate-results.json`、2 スレッド、予算 140）
  - コーパス: 較正コーパスとホールドアウトの 4 コーパスに、意図して作ったコピー 20 組と、関連はあるが別物のファイルを足した 123 ファイル（すべて合成）。
    - コピー: 同名・別名の完全なコピー、Markdown を外したテキスト書き出し、1 行変更 + 1 行追加、1 項目削除した旧版、日本語ノートに 1 文追加、分量だけ変えたレシピ、複数チャンクの長いノートの 1 節を変更、段落を 1 つ追加、PDF の完全コピーと 1 行足して作り直した PDF、画像の 50%・33%・25% 縮小、JPEG 化（品質 70・50・40）、4%・8% の切り抜き、75% 縮小 + 明るさ変更。
    - 別物: ライ麦版に書き換えたサワードウのノート、同じ見出し構成の週報 2 件、最初の節だけ同じ長いノート、別の都市の天気アプリ、色違いのチェス盤、別の店のレシート、別の名前の組織図、同じ形式で数値が少し違う電気使用量のグラフ、同じ書式の 3 か月分の給与明細。ほかに、もともとのコーパスの同じ種類の組すべて（text 2135 組、pdf 33 組、image 981 組）。
  - 結果（値は min(平均どうし, 最良チャンクどうしの上限)。上限には全チャンク対の最大値を使う）

    | 種類 | コピーの最小 | 別物の最大 | しきい値 | まとまらなかったコピー | まとまった別物 |
    |---|---|---|---|---|---|
    | text | 0.927（段落追加）、それ以外は 0.959 以上 | 0.986（給与明細、組の変化 32% で除外）、次は 0.923（ライ麦版のサワードウ） | 0.95 + 組の変化 18% 以下 | 段落追加の 1 組 | なし |
    | pdf | 0.992 | 0.724 | 0.95 | なし | なし |
    | image | 0.975（25% 縮小 + JPEG 品質 50）、それ以外は 0.982 以上 | 0.999（数値違いのグラフ）、次は 0.970（色違いのチェス盤） | 0.98 | 25% 縮小の 1 組 | 数値違いのグラフの 1 組 |

  - しきい値は、別物をまとめない側に寄せた。text の 0.95 は、ライ麦版（0.923）と週報（0.883）より上で、1 行程度の編集（0.959 以上）より下。段落を足した版（0.927）はライ麦版と区別できないので、別の結果として残す。image の 0.98 は色違いのチェス盤（0.970）と別の都市の天気アプリ（0.940）より上。
  - 実際の検索: 較正のテキストクエリ 47 件、無関係なクエリ 36 件、画像クエリ 9 件（上位 10 件、弱い一致も含む）で、できたグループは 27 種類。誤ってまとめたのは、数値違いの電気使用量グラフだけだった（9 クエリ）。
- 限界: 埋め込みは細部より構図や話題を見るので、棒の高さが少し違うだけのグラフはまとまる（コサイン 0.999 で、コピーとも区別できない）。逆に、段落を足したノートや小さなサムネイルは別の結果に残る。コーパスは小さく合成なので、目安として扱う。

## チャンク分割

- 1 チャンクは 384 トークン、重なりは 48 トークン（トークン数は本文のみで数える）。
  - 改行のトークンも、その改行がある行の分として数える。以前は数えておらず、箇条書きや空行の多いノートでチャンクが上限の 1.5〜5 倍になっていた。
- 分割の方法
  - トークナイザのオフセットから行ごとのトークン数を求め、行単位で詰めていく。
  - 1 行が上限を超える場合だけ、トークン境界で切る。
  - 重なりは行単位で前に戻って作る。直前の行が重なりの残りより長いとき（1 段落 1 行の Markdown など）は、その行の末尾をトークン境界で切って重ねる。
  - チャンクは空行から始めない。
  - チャンクが半分以上埋まっていれば、Markdown の見出しの手前で区切る。
- テキストでは文字オフセットと行範囲を保存し、検索結果に `file.md:12-30` の形で示す。
- PDF ではページをまたがずに分割し、ページ番号を保存する。文字が 8 字未満（数字・記号・空白は数えず、CJK は 2 字と数える）のページは捨てる。図だけのページのテキスト層が「5」だけ、といったチャンクが無意味なクエリの上位に来ていたため。
- スニペットは端末の表示幅（全角は 2 桁）で切る。日本語のクエリは空白で区切れないので、2〜4 文字の部分文字列（かなだけのものは除く）も探して、その位置を中心に切り出す。
- 384 トークンにした理由
  - 512 トークンより、検索結果の位置を細かく示せる。
  - CPU のスループットは、この長さではトークン数にほぼ比例するので、ほとんど変わらない。

## 差分更新と中断・再開

- 走査で得た (size, mtime_ns) を索引と比べる。
- 移動・改名したファイルは、消えたファイルと SHA-256 が一致すれば、埋め込みを再計算せずに行のパスだけを書き換える。画像は同じ予算なら常に、テキストと PDF はファイル名（埋め込むタイトルの一部）が同じ場合だけ。写真フォルダの整理で何時間も再計算しないため。
  - 両方一致: 変更なしとしてスキップする。
  - サイズが同じで mtime だけ違う: sha256 で中身を比べ、同じなら mtime だけ更新する。
  - それ以外: 埋め込み直す。
- 走査した root の配下で索引にあるのに見つからなかったファイルは、索引から消す。
  - 新たに ignore 対象になったファイルも、見つからない扱いになるので消える。
  - 例外として、`--no-images` を付けた実行では既存の画像を消さない。
  - 一覧を取れなかったフォルダ（権限、不安定なネットワークドライブなど）の配下も消さない。読めなかったフォルダは実行後に表示する。
  - `--max-size` はその実行だけの指定なので、既定の上限以下でそれより大きいだけのファイルは消さない。
- root にはフォルダだけでなく、単独で指定したファイルも記録する。引数なしの `index` はそれらも更新し、消えたファイルの root は索引から外す。フォルダの root は、消えていても（外付けドライブが外れているだけかもしれないので）飛ばすだけにする。
- root とファイルのパスは realpath（シンボリックリンクを解決したもの）で保存する。macOS と Windows ではディスク上の大文字小文字に合わせる。同じフォルダを別の綴りで指定しても二重に索引しない。
- 処理の順番は、テキスト、PDF、画像。早く終わる種類から検索できるようにするため。
- テキストのチャンクは、ファイルをまたいで最大 32 件までまとめてバッチ推論する。
- 埋め込みが済んだファイルは、約 3 秒ごとに 1 トランザクションでまとめてコミットする。
  - Ctrl-C を受けたら、済んだ分をコミットして終了コード 130 で終わる。
  - 次に同じコマンドを実行すると、残りのファイルから再開する。
  - 実際に途中で中断し、再開できることを確認した（17/23 で中断し、残り 6 件を処理して完了）。
- 失敗したファイルの扱い
  - 読めない・壊れているファイルは `error`、小さすぎる画像・スキャン PDF・バイナリは `skipped` として記録する。
  - どちらも、ファイルが変更されるまで再試行しない。
  - ただし PermissionError など環境が原因のエラーは毎回再試行する。chmod では mtime が変わらないため。
  - モデルの推論が失敗したファイル（ONNX Runtime のメモリ確保失敗など）も `EmbedError: ...` として記録し、毎回再試行する。ファイル自体は正常かもしれないため。
  - 1 ファイルの失敗で全体を止めない。テキストのバッチ推論が失敗したときは、ファイルごとに推論し直し、失敗したファイルだけを `error` にする。
  - 想定外の例外で止まるときも、済んだ分はコミットしてから終わる。
- 走査のルール
  - 隠しファイル・隠しディレクトリ（Windows では hidden / system 属性、macOS では UF_HIDDEN フラグも。`~/Library` など）は対象外。
  - `.gitignore`、`.ignore`、`.anygrepignore` はディレクトリの階層ごとに適用する（pathspec の GitIgnoreSpec）。git と同じく深い階層のルールが優先し、`!` で再び含めることもできる。
  - root より上のフォルダの ignore ファイルも、git リポジトリのルートか、すでに索引している root まで遡って適用する。サブフォルダだけを索引しても、親を索引したときと結果が変わらない。
  - ただし、上の ignore ファイルが root 自身（または root までの途中のフォルダ）を除外している場合は、上のルールを使わずに索引し、どの ignore ファイルを無視したかを表示する。リポジトリ内で gitignore した `private/` や、`*` を無視する dotfiles リポジトリの中の `~/notes` を名指ししたときに 0 件になるのを防ぐため（`rg PATH` と同じく、名指しを優先する）。
  - 親の root を索引するとき、その配下にある別の root（上記のように親のルールでは除外されるもの）の行は消さない。
  - 走査で 1 件も見つからなかったときは、除外・非対応・サイズ超過の件数を表示する。
  - 一覧を取れないフォルダは飛ばし、全体は止めない。
  - `node_modules`、`__pycache__`、`site-packages`、`pyvenv.cfg` のあるディレクトリは除外する。
  - シンボリックリンクはたどらない。
  - UTF-8 として表せないファイル名は除外する。SQLite に保存できないため。
- 進捗バーの ETA は推定コストで重み付けする。
  - テキスト: バイト数 ÷ 4 をトークン数とみなし、800 トークン/秒で換算する。
  - 画像: 予算ごとの秒数で見積もる。
- 処理世代（`config.PROCESSING_GENERATION`）
  - 索引の互換性は 3 つの値で分けて扱う。schema の版は表の構造、モデルのリビジョンはベクトル空間、処理世代は同じモデルでファイルをどうチャンクとベクトルにしたかを表す。
  - files の各行に、処理したときの世代を記録する。meta の `processing_generation` は、索引全体がその世代に揃ったときに記録する。世代を記録する前の索引の行は世代 1 とみなすので、更新しただけでは何も作り直さない。
  - 世代を上げるときは `GENERATION_CHANGES` に、変わったファイルの種類を書く。次の更新（`anygrep index`、検索前の索引、`Index.update()`、バックグラウンドの索引）は、その種類で古い世代のファイルを、変更されたファイルと同じように処理し直す。進捗バーに乗り、中断しても次の実行で残りから続く。同じ中身の画像のベクトルのコピーや、移動したファイルの行の再利用は、古い世代の行からは行わない。
  - 書き込まない検索（`--no-index`、`--everywhere`、別の writer が動いているときなど）は、古い世代の行もそのまま検索し、検索範囲に残っている件数を stderr に 1 行出す。API は `Index.update_pending`、`anygrep status` は `Outdated:` の行で示す。
  - 世代を上げる変更: テキストや PDF の抽出（HTML の扱い、文字コードの判定、ページを飛ばす条件など）、チャンクの長さ・重なり・区切り方、文書側のプロンプト（`title: ... | text: ...`）、画像の前処理（縮小、向き、パッチへの分割）。
  - 世代を上げない変更: クエリ側だけの変更（クエリのプロンプトを変えたら、しきい値を較正し直す）、しきい値、まとめ表示、出力形式、走査の規則（ignore 規則の変更は、ファイルの追加・削除として通常どおり反映される）、索引に保存済みのテキストだけから作れるもの（文字一致の表など）。
  - モデルのリビジョンが違う索引は、これまでどおり開かずに `reset` を求める。違うベクトル空間を 1 つの索引に混ぜないため。
- 書き込みのロック: `index`・`remove`・`reset` と検索前の索引は、索引ファイルの横の空ファイル（`index.sqlite-lock`）に SQLite の排他ロック（`BEGIN EXCLUSIVE`）をかけ、実行の間ずっと持つ。索引本体のトランザクションは数秒ごとの短いものなので、それだけでは「別のプロセスが索引中」を判定できないため。OS のファイルロックなので POSIX と Windows で同じに動き、プロセスが落ちれば外れる。ロックが取れない `index`・`remove`・`reset` は終了コード 2、検索は索引せずにその時点の内容を検索する。

## 検索前の自動索引

`anygrep QUERY [PATH ...]` は、検索する PATH（既定はカレントフォルダ）の配下の新規・変更ファイルを、検索の前に索引する。初回でも `anygrep index` を先に打たずに使えるようにするため。stderr が端末のとき（進捗が見えるとき）は、確認なしで全部を進捗バー付きで索引してから検索する（Ctrl-C で保存して終了 130、次回は続きから）。stderr が端末でないとき（スクリプト、cron）は、時間の予算（既定 30 秒、`--index-budget`、`ANYGREP_INDEX_BUDGET`）で区切り、全部か何もしないかのどちらかにする。

- 手順
  - ホームフォルダ、その親、ドライブのルートは歩かない（索引済みの配下だけを検索し、`anygrep index` でフォルダを指定するよう案内する）。
  - `plan()` で走査する。端末では打ち切らず、1 秒後から見つけたファイル数を 1 行で出す。端末でなければ 2 秒か 20,000 エントリで打ち切り、打ち切ったら何もせずに索引済みの分を検索する。
  - 処理順は文章 → PDF → 画像（新しい順）。中断しても安く、よく検索されるものから見つかる。
  - 削除・移動・mtime だけの変更は安いので常に反映する。
  - 端末でなければ、新規・変更ファイルの推定時間が予算以内（または `-y`）なら全部埋め込んでから検索する。超えるなら何も埋め込まない。PATH の配下に索引済みのファイルがあればそれを検索し、最後に `anygrep index PATH` を stderr に出す。1 件もなければコマンドを示して終了コード 2。確認は出さない。推定時間は判定にだけ使い、表示しない。
  - 既存の root の外の PATH を埋め込んだときは、その PATH を root にして、`anygrep rm PATH` で戻せると表示する。
  - 別のプロセスが書き込みロックを持っていれば索引せず、その時点の内容を検索する。それが `anygrep index --background` のジョブなら、結果のあとにジョブの進捗を 1 行出す。
- 推定時間: `estimate_cost()` の合計に、実測から学んだ係数（meta の `throughput_factor`）を掛ける。係数は実測秒数 ÷ 推定秒数で、20 秒以上埋め込んだ実行ごとに α = 0.5 の指数移動平均で更新し、0.5〜4.0 に収める。測る前は控えめに 1.5 とする。`anygrep status` に「measured speed」として出る。デモコーパス（23 ファイル）は 2 スレッドで推定 18 秒、実測 32 秒（モデルの読み込みを含む）だった。
- `--no-index` と `--everywhere` は索引を読み取り専用（`mode=ro`）で開き、何も書かない。cron の索引と並べても安全。

## モデルのダウンロード

- urllib で、必要なファイルだけを固定したリビジョン（`daa72c5…`）から取得する。
  - 途中で止まっても `.part` ファイルと Range ヘッダで続きから再開できる。
  - urllib はサーバーが途中で接続を閉じても例外を出さないので、受け取ったサイズを確認し、足りなければ同じ実行の中で続きから取り直す（最大 5 回、間隔は 1, 2, 4... 秒）。読み込み中の接続リセットやタイムアウトも同じく取り直す。
  - サーバーが Range を無視して 200 を返したら最初から書き直す。416 なら `.part` を消して最初から取る。
  - `.part` がすでに完全なサイズなら、ハッシュを確かめてそのまま使うか、壊れていれば消して最初から取る（Range を送ると 416 になるため）。
  - 取得後に SHA-256 を照合する。
  - 照合が済んだファイルには `.verified` マーカー（サイズ・mtime・ハッシュ）を書き、次回以降は再ハッシュしない。
- huggingface_hub は使わない。依存を増やさず、挙動を自分で制御するため。
  - ミラーを使いたい場合は `HF_ENDPOINT` を指定する。
- `ANYGREP_OFFLINE=1` または `HF_HUB_OFFLINE=1` のときはネットワークに一切触れない。足りないファイルの URL と置き場所を表示して終了する。
- テレメトリはない。ネットワークに接続するのはモデルのダウンロードだけ。

## 実測（デモコーパス、Ryzen 7 7700、4 スレッド、他ジョブ稼働中で loadavg 4〜9）

| 項目 | 結果 |
|---|---|
| 全件の索引作成（ノート 12、PDF 3 件 8 ページ、画像 8、予算 140） | 約 19 秒 |
| 画像 1 枚あたり | 予算 70 で 0.91 秒、140 で 1.7 秒、280 で 3.6 秒 |
| テキストのみの検索 1 回（プロセス起動とモデルのロードを含む） | 約 1.5 秒、RSS 0.5 GB |
| 画像クエリ 1 回 | 約 3 秒 |
| 索引作成時のピーク RSS | 1.28 GB |
| 変更なしでの再実行 | 0.2 秒 |
| 12 クエリの top1 正解 | 予算 70 と 140 で 12/12、280 で 11/12（外れた 1 件も、もっともらしい別のノートが 1 位） |
